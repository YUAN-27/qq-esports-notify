## 1. 功能定位与边界

### 1.1 做什么

群友在比赛**开赛前**的一段时间窗口内（今日总预告发布起），通过 `@机器人 /bet` 对已预告比赛的**胜者**下注；
比赛结果由既有的战果结算管线判定（不新增任何抓取），猜中的群友**+1 积分**，
机器人发一条开奖消息并列排行榜。免费玩、无消耗、纯群内娱乐。

三个设计支柱：

1. **零网络**。`/bet` 的任何子命令都不抓 Liquipedia、不调 Cito —— 可下注列表直接读
   `state_results_pending.json`（`note_pending` 登记的清单，字段现成）。
   这与 `--announce`（零网络）同哲学，也天然满足铁律「绝不在持有状态锁时联网」。
2. **不碰既有管线**。预告、开赛提醒、战报、整合版**一条消息的版式都不改**（v1）；
   竞猜是挂在旁边的平行功能，停掉 `bet_enabled` 后行为与今天完全一致。
3. **状态可推导的绝不存**。竞猜回合的开/封状态是 `f(now, est, bo, 配置)` 的**纯函数**，
   不落盘；落盘的只有「谁押了谁」和「每个人的分」。

### 1.2 v1 明确不做什么

| 不做 | 为什么 |
|---|---|
| 押注积分（有消耗的货币） | 免费玩零门槛；有消耗就要做退款、审计、纠纷，复杂度翻几倍 |
| 撤单 | 改单（封盘前任意改）已覆盖「改主意」；撤单还会让开奖时的参与人数对不上 |
| 猜比分 / 猜地图数 | 判定面太宽（Bo3 的 2:0/2:1、加时、重赛），v1 只猜胜者 |
| 封盘主动提醒 | 一天几场 × 一条提醒 = 与开赛提醒/战报形成消息轰炸；列表里显示封盘时刻足够（v1.1 再评估） |
| 实时比分推送 | 那是另一条产品线；本功能只借用「终局结果」 |
| 多群隔离 | 当前只有 `1056302577` 一个群；数据结构**按群分桶**（round 带 `group`），多群就绪但不用 |

### 1.3 🔴 硬前提：`douyu-cmd` 还没上线

`/bet` 是群内命令，**寄生在 `esports.py --listen` 这个常驻进程上**。截至 2026-10-09 的部署状态：
`douyu-cmd.service` 已装到 `/etc/systemd/system`（带 `[Install]`），但
**`is-enabled=disabled` / `is-active=inactive`，从未启动**（按 `CMD_INTERACT.md` §9.4 的上线顺序待办）。

所以 `/bet` 的上线顺序天然是两段：**先把 `/赛事` 跑通（前台手跑 → 群内确认 →
`systemctl enable --now douyu-cmd`），再开 `bet_enabled`**。详见 §12。

## 2. 命令设计

### 2.1 语法表

一律 `@机器人` + 命令（沿用 `/赛事` 的触发方式；不 @ 不响应，避免误触发）。
中文关键词，因为群是中文群（6 个人），不提供英文别名（YAGNI）。

| 命令 | 作用 | 说明 |
|---|---|---|
| `/bet` | 可下注列表 + 我当前的押注 | 零参数，默认动作 |
| `/bet 我的` | 我的记录（积分 / 命中率 / 每场状态） | |
| `/bet 排行` | 排行榜 TOP 10 | |
| `/bet 规则` | 规则说明（开收时间、算法、积分） | |
| `/bet <编号> <A\|B>` | 下注 / **改单** | 编号 1–99；`A`/`B` 大小写不敏感，`1`/`2` 同义 |

**没有撤单**：封盘前改单自由（再发一次 `/bet 1 B` 即覆盖），但没有「不赌了」这个动作 ——
理由见 §1.2。改单的回复会回显原选择，避免「我到底改没改」的疑惑。

### 2.2 参数白名单（🔴 命令识别第一次从「精确匹配」扩展到「带参数」）

现有 `parse_command` 是「剥 CQ 码后**整条恰好相等**」才算命令（`CMD_INTERACT.md` 闸门 1）。
`/bet 1 A` 这种带参数的形式是这套机制的第一次扩展，规则：

```
输入 → 剥 CQ 码（含 [CQ:reply,...]）→ strip() → 全角空格/制表符归一成单个半角空格
     → 按空格切 token（最多 2 个）
     → 第一 token 必须是 "/bet"（其后必须是空格或行尾 —— "/betx" "/bet1" 一律不认）
     → 第二 token（可省）过白名单：
         ""            → 列表
         "我的"        → 我的记录
         "排行"        → 排行榜
         "规则"        → 规则说明
         <编号> <选项> → 下注（编号 = ^[1-9][0-9]?$；选项 = ^[ABab12]$，1→A、2→B）
```

白名单外的任何输入（`/bet 1 C`、`/bet 0 A`、`/bet 100 A`、`/bet 1 A B`、`/bet 1`）
**不静默吞掉**，回一条用法提示（见 §2.5）—— 带参数的命令必须有反馈，否则用户不知道
错在哪。回用法提示算「真回复了」，水位线照常推进。

⚠️ 扩展的回归风险：`/赛事` 的精确匹配路径**一行不改**（`CMD_REGISTRY` 原样），
`/bet` 走新增的前缀分支。自检用 AST 断言 + 变异测试钉住（§11 断言 1、2）。

### 2.3 编号是什么、会不会漂

编号 = **当前可下注列表里的行号**，列表由 `state_results_pending.json` 生成：

- 排序：**可下注/未开放的按 `ts` 升序排在前**，已封盘/已开奖/已取消的按 `ts` 降序垫后
  （保证第 ①② 行永远指向当下最该看到的比赛，不会被陈年旧场次挤掉）；
- 上限 `bet_max_list_rows`（默认 12）行，超出显示「等 N 场」；
- **会漂**：清单条目在结算 36 小时后被 `_prune_pending` 清掉，行号会前移。
  这是可接受的 —— 编号只在「刚看完列表 → 立刻下注」这个几秒的时间窗里有意义，
  且**下注/改单的回复一律回显队名**（「已记录 ①：猜 Vitality 胜」），
  回显即消歧。`/bet 我的` 里也永远显示队名而非编号。

### 2.4 A/B 是什么

`A` = 列表里排前面的队（`teams[0]`），`B` = 排后面的（`teams[1]`）。
**为什么不用队名当下注参数**：队名的写法/别名/大小写是出了名的坑
（`CITO_TEAM_ALIASES` 那四条别名就是这么来的：`1w Team` vs `1win`、`Natus Vincere Junior`
vs `NAVI Junior`……），用 A/B 零歧义、零别名维护。队名只在**机器人的回显**里出现。

下注记录存的是**队名快照**（`pick_team`）而不是 `A/B`：`absorb_result` 在结算时会用
结果页的写法**改写** `it["teams"]`（esports.py:2893），顺序和措辞都可能变；
按名称匹配才稳（§6.2）。

### 2.5 回复模板全集

所有回复都带 `[CQ:reply,id=<message_id>]` 前缀（与 `/赛事` 一致，群里看得出是回哪条）。
队名单个截断到 16 字符（超出补 `…`，看得出是刻意截断）；昵称截断到 12 字符（净化规则见 §10 坑 1）。
时间一律 `HH:MM`，跨天加标记：未来「次日 / N 天后」，往日「昨天 / MM-DD」—— 列表会把
已封盘/已开奖的场次垫在后面（只留最近的，`bet_max_list_rows` 条），往日行没日期会被
误以为是今晚的下一场（2026-10-12 灰度实测踩坑，三处展示层修复见文首「实现落地记录」）。

## 3. 时间窗口规则（核心）

> **v2（2026-10-12 用户要求，已上线）**：下注窗口 = **今日总预告发布（09:30 登记）→
> 每场开赛前 10 分钟封盘**，各赛制一致。v1 是「开赛后开放、赛中封盘」，
> 改 v2 的原因见 §3.4。

### 3.1 四个时刻

| 名字 | 定义 | 出处 |
|---|---|---|
| `reg_ts` | **登记时刻 = 今日总预告发布时刻**（09:30 那轮 `note_pending`） | v2 新增字段，写进清单条目 |
| `est` | **登记 ts = 计划开赛时刻** | `note_pending` 写进清单的 `ts`；与结算窗口同一锚点 |
| `close` | **封盘线 = `est − bet_close_before_start_minutes`**（默认 10 分钟） | 竞猜新增，不落盘、现算 |
| `grace` / `timeout` | 既有结算窗口（开始抓结果 / 放弃） | 不改：`{Bo1:50,Bo3:100,Bo5:170}` / `{Bo1:150,Bo3:270,Bo5:360}` |

**开放时刻 = `reg_ts`**（纯时间判定 `now ≥ reg_ts`）。条目只在登记后才存在于清单里，
所以「上了今日总预告」与「可以下注」是同一时刻；赛中才被 Liquipedia 发现的新场次，
在它进清单（= 被登记）的那一刻同样开放。旧条目没有 `reg_ts` 字段，读取时缺省为 0
（= 早已登记、默认开放）—— 上线日不影响存量数据。

### 3.2 封盘线公式（v2）

```
close = est − bet_close_before_start_minutes × 60      （秒）
```

**各赛制一致**：Bo1/Bo3/Bo5/认不出的赛制全是 `est − 10 分钟`。v1 按赛制
（Bo1 +35 / Bo3 +85 / Bo5 +155 分）是因为封盘线要锚在机器人抓结果的 `grace`
之前；v2 封盘线在开赛前，与「比赛打多久」彻底无关，赛制维度随之消失。

`bet_close_before_start_minutes` 默认 **10**（可配，钳制 **0~60 分钟**）：
- 取 10 而不是 0，是给 `est` 滑点留缓冲（Liquipedia 的计划时刻常晚 30–60 分钟，
  但也存在提前开赛）；提前封优于踩点封；
- 钳制上限 60 分钟是防配置手误（如填 999）把封盘线压到登记时刻之前 →
  所有比赛「出生即封盘、静默不可押」。规则文案与封盘线共用同一个钳制函数，
  配置改了文案不会说谎（自检断言钉住）。

### 3.3 实例

`est = 今天 21:00`，Bo3，09:30 登记：

```
09:30 ┌─────────── 开放下注 ───────────┐21:00 ┌──── grace ────┐
登记  │                                 │开赛   │                │
(总预告│  群里随时 @机器人 /bet 1 A/B    │      │ 22:40 起某轮   │
 发布)│  封盘前可随时改单                │      │ --results 判定 │
      └─────────────────────────────────┘20:50 └─ reported ─→ 结算竞猜
                                        封盘                     + 开奖消息
```

用户视角的一天：09:30 总预告发布（**竞猜同时开放**）→ 白天任意时刻可下注 →
20:50 封盘 → 21:00 开赛 → 22:40 后某轮 `--results` 判定 → 战报 + 开奖两条消息。

### 3.4 为什么从「赛中封盘」改成「开赛前封盘」（v2 动机）

v1（开赛后开放、`grace − 15 分`封盘）有两个结构性问题：

1. **信息不对称**：封盘时比赛还在打，群里观众自己看着比分下注 —— 竞猜的
   公信力没了。v1 文档 §3.6 局限 1 写明「要信息对称就得改成开赛前截止，
   那是另一个产品」；v2 就是把这个开关合上。
2. **Bo5 要打三小时**：封盘线 +155 分意味着下注窗口横跨大半个系列赛，
   中途改期/取消全走到期作废，体验割裂。

v2 把窗口整体挪到开赛前，「不晚于机器人知情」这条安全属性仍然成立
（而且更强了：封盘时刻严格早于开赛，更早于机器人知情）；代价是
`est` 滑点时用户少押一段 —— 取舍同 v1 的哲学：**早封优于晚封**。

### 3.5 硬兜底（时间判定的第二道闸）

无论时间判定出什么，**清单条目 `status != "pending"` 时一律拒绝下注**
（`reported` / `abandoned` 都拒）。判定顺序永远是**先查 status，再查时间**。
`reg_ts` 缺省 0 是第三层兜底：老数据不会卡在「未开放」。

### 3.6 已知局限（诚实清单，写进文档不写进群）

1. **`est` 滑点**：计划时刻可能晚 30–60 分钟，于是「比赛实际还没打，
   竞猜已封盘」。早封优于晚封（v1 §3.4 的哲学原样保留）。
2. **开赛前 10 分钟内才登记的场次出生即封盘**（`close < reg_ts`）——
   直接进 `closed`，不静默失效：列表里它是参照行，`/bet N X` 回「已封盘」。
3. **Liquipedia 改期**：登记后页面改时间不会更新 `ts`（`note_pending` 只增不改），
   一切以登记时刻为准。改期后的「新」场次若被再次预告，会是新条目（键含 `ts`），
   旧条目的竞猜走到期作废（§6.4 终局 3）。
4. **封盘线配置钳制 0~60 分钟**：超出按边界算，与规则文案同源（不会说谎）。

## 4. 状态机（每场竞猜回合）

```
                 now < est                    est ≤ now < close              close ≤ now
 status=pending  ┌─────────┐  时间到   ┌─────────┐  时间到   ┌─────────┐
                 │ upcoming │ ───────→ │  open   │ ───────→ │ closed  │
                 └─────────┘           └─────────┘           └─────────┘
                                                                    │
   status=reported ─────────────────────────────────────────────────→┤ 结算（对账循环）
   status=abandoned ────────────────────────────────────────────────→│ 作废/待backfill补救
                                                                    ↓
                                                              §6.4 五种终局
```

`bet_round_state(item, now, es)` 是**纯函数**（不落盘、不读 bets 文件）：

| 条件（按序判定） | 状态 | 可下注 | 列表里显示 |
|---|---|---|---|
| `status == "reported"` | `settled` | 否 | 「已开奖」+ 比分 |
| `status == "abandoned"` | `cancelled` | 否 | 「赛事取消」 |
| `now < est` | `upcoming` | 否 | 「HH:MM 开放」 |
| `now < close` | `open` | 是 | 「HH:MM 封盘」 |
| 其余 | `closed` | 否 | 「已封盘」 |

⚠️ 顺序即语义：**status 判定永远在时间判定之前**（§3.5）。

## 5. 数据模型

### 5.1 `state_bets.json`（新状态文件，运行期产物）

按项目铁律归类：**绝不进仓库、绝不进 `deploy.zip`**（`.gitignore` + `pack_deploy.is_runtime_state()`
双守卫，与 `state_results_pending.json` 同等待遇；`.lock` 文件同理）。

```jsonc
{
  "version": 1,
  // 每个「有人押过的比赛」一个 round。键 = _item_ident(item) = (队名规范键, 登记 ts)，
  // 与 note_pending / absorb_result 用的是同一把键 —— 读日志时它们是同一个「这一场」。
  "rounds": {
    "vitality|navi|1760000000": {
      "group": "1056302577",
      "teams": ["Vitality", "NAVI"],     // 下注时看到的队名快照（A=teams[0]）
      "ts": 1760000000,                  // 登记 ts（= est）
      "bo": "Bo3",
      "tour": "BLAST Premier Fall Final",
      "close_ts": 1759999400,            // 建 round 时按当时的配置算定存下来：
                                          // 中途改配置不影响已有人下注的场次（公平）。
                                          // v2 = ts − 600（开赛前 10 分钟）
      "bets": [
        // 一个用户一场只有一个元素 —— 再下注即覆盖（改单）。changed 记被改过几次。
        {"uid": "123", "nick": "群友A", "pick": "A", "pick_team": "Vitality",
         "at": 1760000100, "changed": 0}
      ],
      // 未结算 = null。结算是一次原子写（加分 + 标记 + 统计同在一把锁里）。
      "settled": null,
      // 结算后：
      "settled": {
        "at": "2026-10-12 22:47:00",
        "winner_team": "Vitality", "score": "2:1",
        "void_reason": null,             // null=正常开奖；"expired"/"undecidable"=作废
        "announced": false,              // 开奖消息发出去才 true（尽力，可重试）
        "announce_tries": 0
      }
    }
  },
  // 积分表。uid 为键；nick 每次下注时刷新（群名片会变）。
  "users": {
    "123": {"nick": "群友A", "pts": 5, "hits": 5, "total": 6}
    // hits/total 只统计正常开奖的场次（猜中/猜错）；作废场次不计入 ——
    // 比赛取消不该惩罚命中率。
  }
}
```

### 5.2 为什么 round 懒创建（第一个下注时才写）

- 注册即建 round → 每轮预告都给没人押的比赛写一次状态，纯浪费；
- 懒创建下，**没有下注的比赛在 `state_bets.json` 里不存在**，文件大小与群活跃度成正比；
- 对账循环天然只处理「有人押过的」（`rounds` 里有的），没人押的零开销。

### 5.3 为什么 `pick` 存队名快照而不只存 A/B

`absorb_result`（esports.py:2893）在结算时用**结果页的写法**覆盖 `it["teams"]`
—— 顺序可能翻、措辞可能变（`Team Vitality` → `Vitality`）。所以：

- 下注时把 `pick_team`（那一刻的队名）和 `pick`（A/B）都存；
- 结算时**按名称匹配**：`winner == pick_team` → 猜中；名称对不上时退化到规范化比较
  （小写、去空格/连字符/标点，与 `_teams_key` 同源的归一）；再对不上 → `undecidable` 作废（§6.4 终局 4）；
- 只存 A/B 会在「顺序被翻」时**系统性判反**，且没有任何报错 —— 典型的静默错误，必须从数据模型上避免。

### 5.4 锁纪律

- `update_bets(apply_fn)`：新写的「锁内**重读 → 应用 → 写回**」助手，与 `update_pending`
  完全同构（跨进程 `flock` 锁在**独立的 `state_bets.json.lock`** 上，不锁状态文件本身 ——
  rename 替换的老教训）；
- **绝不在持锁时联网**：`/bet` 全路径零网络，结构上满足；结算对账里「加分」在锁内、
  「发开奖消息」在锁外，两段分离（§6.2）；
- 锁只包住「读改写」，不做渲染、不发消息 —— 渲染/发送全在锁外。

## 6. 判定与结算

### 6.1 对账循环，而不是「顺手结算」

🔴 **这是本文最重要的一个结构决定。** 直觉做法是在 `run_results` 判定 `reported` 的
那一刻顺手结算竞猜。否掉，理由是崩溃缺口：

```
results 进程：① 锁内把 item 标成 reported（落盘）── ② 顺手结算竞猜 ── ③ 发开奖消息
                                  ↑ 在这里崩了 / 被 kill / 停电
```

第 ① 步已完成 → 下一轮 `run_results` 看到该场 `status=="reported"` **直接跳过**
（只认 reported 的不重抓）→ 第 ② 步永远不会再执行 → **这场竞猜永远不结算，
押了的人永远看不到开奖**，而且没有任何报错。

正确做法：**结算是幂等的对账，不是事件回调**。`run_results` 末尾（每轮都跑）扫一遍清单：

```
对账（每轮 --results 尾部执行，零网络，纯本地）：
  for item in pending 清单:
      if item.status != "reported":  continue        # abandoned 的不动（等 backfill 补救）
      round = rounds.get(_item_ident(item))
      if round and not round.settled:  _settle_one(round, item)
  # 过期清扫：清单里已没有、但 rounds 里还挂着的未结算 round（被 _prune_pending 清掉了）
  for key, round in rounds.items():
      if not round.settled and key 不在清单 and round.close_ts 早于 results_max_age_hours:
          标记 settled(void_reason="expired")          # 静默作废，不加分
```

对账的三个好处：崩溃恢复天然支持（下轮继续）、重复执行无害（`settled` 即幂等锁）、
`backfill_abandoned` 把取消场次救回 `reported` 后**下一轮自动补结算**（§6.4 终局 1 的
救援路径，不需要额外代码）。

### 6.2 结算原子性与消息尽力

```
_settle_one(round, item):
    # 第一段：锁内，原子。加分、统计、标记 settled 一次写完。
    def _apply(data):
        r = data["rounds"].get(key)
        if r is None or r.get("settled"):  return None        # 幂等：已结算直接返回
        winner = item.get("winner")                            # absorb_result 写的胜者名
        correct = [b for b in r["bets"] if _pick_hits(b, winner, r["teams"])]
        r["settled"] = {"at": now, "winner_team": winner, "score": item.get("score"),
                        "void_reason": None, "announced": False, "announce_tries": 0}
        for uid in correct:  users[uid].pts += pts; users[uid].hits += 1
        for b in r["bets"]:  users[b.uid].total += 1
        return r
    r = update_bets(_apply)
    if r is None:  return                                      # 已被别的进程结算过

    # 第二段：锁外，尽力。发不出去也不影响已入账的分。
    if _send_开奖(r):
        _mark_announced(key)                                   # 再一次锁内写，只翻一个布尔
    else:
        _bump_announce_tries(key)                              # 超 bet_announce_max_tries 后放弃
```

要点：

- **加分与 `settled` 标记在同一把锁里** → 绝不会「加了分没标记」（重复加分）
  或「标记了没加分」（吞分）。变异测试钉这一条（§11 断言 5）。
- **消息在锁外** → 满足「绝不在持锁时联网」，发送慢/挂不会堵住其他下注；
- `announced` / `announce_tries` 两段式 → 消息发送失败下轮重发；超过
  `bet_announce_max_tries`（默认 5）后放弃重发（分已入账，`/bet 我的` 状态正确，
  只是群里少一条开奖 —— 宁可少一条，不要每 10 分钟重试一次刷屏）。

### 6.3 积分规则

- 猜中 `+bet_points_per_hit`（默认 **1**）；免费玩，下注不消耗；
- `hits` / `total` 只统计**正常开奖**的场次；作废（`expired` / `undecidable` / 取消）
  不计入 —— 比赛取消不惩罚命中率；
- 排行榜同分按 `pts` 降序、再按**最近一次得分时间**降序（活跃者靠前）；
  并列显示相同名次（不玩 1/2/2/4 那套，6 人小群没必要）；
- 积分只增不减（没有扣分场景）；清空需要手工删状态文件（不提供命令 —— 防误触）。

### 6.4 五种终局

| # | 终局 | 触发 | 计分 | 群消息 |
|---|---|---|---|---|
| 1 | 猜中 | `reported` 且 `winner` 命中 `pick_team` | `+1`，`hits/total +1` | 开奖（进「猜中」名单） |
| 2 | 猜错 | `reported` 且未命中 | `total +1` | 开奖（进「惜败」名单） |
| 3 | 过期作废 | 清单条目被清掉（`abandoned` 36h 后 / 异常丢失），round 仍未结算 | 不计 | **无**（`/bet 我的` 显示「已过期」） |
| 4 | 无法判名作废 | `reported` 但 `winner` 与两个队名都匹配不上（写法漂移） | 不计 | **有**：「本轮竞猜作废（胜者名称与参赛队不一致，已记录日志）」—— 有人押了必须给说法 |
| 5 | 取消待定 | `abandoned` 且条目还在清单里 | 挂起 | **无** —— 等 `backfill_abandoned` 次日补救；救回来走终局 1/2，救不回来终局 3 |

⚠️ 终局 5 的「取消」**绝不立刻作废**：`backfill_abandoned` 会把延期/误判的场次在次日早上
重新配对改回 `reported`。一见 `abandoned` 就作废 + 发作废消息，会被第二天的补结算打脸
（消息已经说出去了，收不回来）。所以取消是**挂起态**，不是终局。

## 8. 边界情况总表

| # | 情况 | 处理 | 理由 / 依据 |
|---|---|---|---|
| 1 | 同一用户重复下注 | **改单语义**：覆盖旧 pick，`changed +1`，回显新旧选择 | 一个用户一场一个元素；覆盖即改单，无撤单 |
| 2 | 封盘时刻竞态（21:24:59.9 的请求 vs 21:25:00 的线） | 时间判定**在锁内**做（读 item → 判时间 → 写 bet，同一把锁） | 防 TOCTOU：锁外判定再锁内写，等于没判定 |
| 3 | 多人同时下注同一场 | `update_bets` 锁内重读-应用-写回；各自 uid 不同元素，互不覆盖 | `update_pending` 同构；实测两进程各 200 条 → 400/400 |
| 4 | 下注请求撞上结算进行中 | 硬兜底：`status != "pending"` 一律拒（§3.5） | 时间判定兜不住时的第二道闸 |
| 5 | 发送失败（NapCat 挂） | handler 返回 `False` → 水位线不推进 → 下轮重试（≤ `cmd_max_attempts=3` 次后放弃并推进） | 既有重试语义；`place` 是幂等 upsert，重试安全（第一次若已写盘，第二次走「已记录」路径） |
| 6 | 内部异常（状态文件损坏等） | handler 自己 try 住 → 静默 + 写日志 → 返回 `False`（走重试，**不在群里回「出错了」**） | 项目铁律：失败不向群里广播 |
| 7 | 首跑 / 序号重置 | 继承 `--listen` 既有铁律：首跑只记水位线，历史一条不响应；`real_seq` 重置则重新基线化 | `CMD_INTERACT.md` 坑 1；`/bet` 无新代码 |
| 8 | `@全体成员` 混入 | `[CQ:at,qq=all]` 不算 @ 机器人 → skip | 既有判定 |
| 9 | 命令里夹带 CQ 码 | 剥 CQ 后过白名单正则；`/bet [CQ:at...]` → 剥成 `/bet` → 当列表命令，无害 | §2.2 |
| 10 | 昵称含 CQ 码/控制字符（伪造 `@全体`） | `_safe_nick()`：剥 `\[CQ:[^\]]*\]`、去控制字符、截断 12 字符后才允许回显 | 🔴 §10 坑 1 |
| 11 | 编号漂移（旧场次被裁，行号前移） | 编号只对「刚看完的列表」有效；回复一律回显队名消歧 | §2.3 |
| 12 | 延后开赛 | 窗口按 `reg_ts` 开、封盘线锚 `est`（比赛实际没打但已封盘） | §3.6 局限 1，早封优于晚封 |
| 13 | 开赛前 10 分钟内才登记 | `close < reg_ts` → 出生即封盘，直接进参照行、不可押 | §3.6 局限 2，不静默失效 |
| 14 | Liquipedia 改期 | 登记 ts 不变；再次预告是新条目（新键），旧 round 到期作废 | `note_pending` 只增不改 |
| 15 | 同一对队伍再打一场（EPL 赛制） | 键含 `ts` → 新 round，旧 round 独立结算 | `_item_ident` 同源 |
| 16 | 比赛 `abandoned` | 挂起（终局 5），等 `backfill_abandoned`；救不回 → 过期作废 | §6.4 |
| 17 | `winner` 名称与队名对不上 | `undecidable` 作废 + 一条说明消息；不加分 | 终局 4；防静默判反 |
| 18 | 抓取失败 / 页面结构变了 | 战报线既有行为（告警/日志）；竞猜对账无 `reported` 可结 → 顺延到下一轮 | 竞猜不新增抓取，无新故障面 |

## 9. 与现有架构的集成点

### 9.1 `parse_command` 的第一次扩展（🔴 有回归风险）

现有：剥 CQ → `strip()` → 整条在 `CMD_REGISTRY` 里才算命令。
扩展后：

```
text = strip_cq(...).strip()
if text in CMD_REGISTRY:            → 既有路径，一行不改（/赛事 零影响）
head, _, rest = text.partition(" ")
if head == "/bet":                  → 新增前缀路径，rest 交 bet_arg_parse(rest)
                                      返回 None = 白名单外 → 回用法提示
```

`/赛事` 的精确匹配是已部署代码，**不许碰**。自检：AST 断言 `CMD_REGISTRY` 仍含
`CMD_SCHEDULE`；变异测试把前缀分支改成「也走精确匹配」→ 断言必须 FAIL（§11 断言 1）。

### 9.2 冷却键：从「群\|命令」到「群\|bet\|用户」（🟠 行为差异，必须显式）

现有冷却键是 `"%s|%s" % (group, cmd)`，**全群维度**：同群同命令 N 秒内只响应一次。
对 `/赛事` 合适（它抓网络，防连点是风控预算）；对 `/bet` **不合适** ——
A 的押注会把 B 在冷却窗内的押注**静默吞掉**（`skip` → 水位线推进，消息真丢了），
而被吞的是一次真实的金钱… 不是金钱，但是真实的参与。6 人群里俩人在封盘前 3 秒同时下注，
是大概率事件。

所以 `/bet` 是第一个**按用户维度**冷却的命令族：

```
冷却键 = "%s|bet|%s" % (group, uid)         # uid 来自消息发送者
冷却值 = bet_cooldown_seconds（默认 5，而不是 cmd_cooldown_seconds 的 30）
```

- 按用户 5 秒：防单人连点，互不阻塞；
- 为什么不是 30：`/bet` **零网络**，30 秒冷却的初衷（Liquipedia 风控预算）不适用；
  且下注是连续动作（看列表 → 下注 → 改单都在几秒内），30 秒会把正常流程打断；
- 实现上 `handle_cmd_message` 的 key 构造为前缀命令开一个口子：解析器额外返回
  `cooldown_key`（精确匹配路径返回 `None` = 用老 key，行为零变化）；
- 附带影响：`_COOLDOWN_MAP_MAX = 50` 的裁剪按最近使用保留，per-user 键在此群规模下
  （≤ 用户数 + 少量命令键）远低于上限，无需改；群规模上百时再评估。

### 9.3 结算钩子：`run_results` 尾部一行对账

`run_results(cfg, args)` 在既有「逐场抓结果 → 发战报」循环**结束后、return 前**，
加一次 `bet_reconcile(cfg, es)`（§6.1 的伪代码）。它只读清单快照 + 读写 `state_bets.json`，
零网络。v1.1 可选在 `run_daily` 尾部也挂一次（兜底 results timer 整晚挂掉的情况；
整合版消息本身不变）。

⚠️ **`run_daily` 的零网络纪律不破**：对账零网络，挂上去也合规；但 v1 先不挂 ——
「整合版顺带补结算」会让「为什么今早才开奖」变得难以解释，宁可让 `/bet 我的` 显示待开奖。

### 9.4 配置项（全部进 `ESPORT_DEFAULTS` + `config.example.json`）

| 键 | 默认 | 说明 |
|---|---|---|
| `bet_enabled` | `false` | 总开关。默认关（与 `cito_enabled` 同哲学）：关着时 `/bet` 只回「未开启」，一行代码路径都不走 |
| `bet_points_per_hit` | `1` | 猜中得分 |
| `bet_close_before_start_minutes` | `10` | 封盘线 = `est − 此值`（§3.2），钳制 0~60 分钟 |
| `bet_cooldown_seconds` | `5` | `/bet` 专属冷却，**按用户维度**（§9.2） |
| `bet_max_list_rows` | `12` | 列表行数上限 |
| `bet_announce_max_tries` | `5` | 开奖消息重发上限（§6.2） |
| `bet_dry_run` | `false` | 灰度开关：回复改走 `console` 通道（落日志不进群），**状态照常变更** |
| `bet_card_enabled` | `true` | 查询类回复（列表/我的/排行/规则）是否发 1920×1080 卡片大图（§14）。**只影响查询**；出不了图自动降级回原纯文本，回滚改成 `false` |

⚠️ `resolve_config` 是 `es.update(user)` **浅合并** —— 这些是标量不是表，没有
「只改服务器 config 就整体顶掉默认表」的问题（那是 `hltv_aliases` 的教训）；
但新增键仍要**同时**进 `ESPORT_DEFAULTS` 和 `config.example.json`，两处漏一处
就会「仓库看着有、服务器上没注释可抄」。

### 9.5 零新增单元 / 零新增网络 / 零新增依赖

- **systemd**：不加。命令走 `douyu-cmd`（已有），对账搭 `douyu-esports-results`（已有）；
- **网络**：`/bet` 全路径零请求（AST 断言钉住，§11 断言 7）；对账只读本地文件；
- **依赖**：`flock` / `json` / `re` / 标准库，与现有代码同一套。

### 9.6 与开赛提醒的触点（v1.1，明确不在 v1）

开赛提醒（`--announce`，每分钟）在 `est` 时刻发 Match Preview 卡。v1.1 的可选项：
在该消息末尾加一行「竞猜已开放：/bet 1 A」—— 这是把两个功能粘起来的最自然触点。
**v1 不做**：改已部署路径的消息版式，按项目纪律必须先渲染真实数据预览给用户确认，
不该塞进一个还没评审的实现里。已在文档登记，作为 v1.1 第一候选项。

## 10. 坑与风险（按危险度排序）

### 🔴 坑 1 · 昵称回显 = CQ 码注入面

开奖消息要列「猜中：群友A、群友B」—— 昵称来自**群名片**，是用户可控字符串。
群里任何人把名片改成 `[CQ:at,qq=all]` 或一长串 CQ 码，机器人回显时就会
**替他去 @ 全体 / 插入任意 CQ 段**。这不是理论攻击，是这条功能自带的注入面。

对策：`_safe_nick(s)` —— 剥掉所有 `\[CQ:[^\]]*\]` 形状的子串、去控制字符（`\x00-\x1f`）、
截断 12 字符，**之后**才允许进入任何回复文本。自检：变异测试把剥 CQ 那行删掉 →
断言必须 FAIL（§11 断言 8）。

### 🔴 坑 2 · 「顺手结算」的崩溃缺口（§6.1 已展开）

`reported` 落盘 → 崩 → 下轮跳过该场 → 竞猜永不结算，且无任何报错。
对策是对账循环 + `settled` 幂等锁。这是本功能与既有管线耦合最深的一处，
实现时**不许**为了「少扫一遍清单」把它改回事件回调。

### 🟠 坑 3 · 全群冷却吞掉别人的押注（§9.2 已展开）

复用 `cmd_cooldown_seconds`（全群 30 秒）会让 `/bet` 在 6 人群里互相踩。
按用户 + 5 秒。改的是 `handle_cmd_message` 的 key 构造，**精确匹配路径的行为零变化**。

### 🟠 坑 4 · handler 返回值语义：什么算「失败」

`handle_cmd_message` 的契约：`True` = 真回复了（水位线推进 + 记冷却）；
`False` = 失败（水位线不推进，最多重试 `cmd_max_attempts=3` 次后放弃）。
对 `/bet`：

- 任何**确定性拒绝**（未开放/已封盘/编号错/选项错/未开启）→ 回了消息 → `True`；
- **发送本身失败**（`send_with_retry` 没送达）→ `False`（下轮重试，幂等安全）；
- **内部异常** → 自己 try 住、静默 + 日志 → `False`；
- ⚠️ 绝不要对确定性错误返回 `False` —— 那会让同一条命令每轮重试 3 次，
  白烧 3 次发送机会，还可能把后面的命令堵在暂停扫描里（`wm_after_handle` 的 `cont=False`）。

### 🟠 坑 5 · 编号漂移造成「押错场」

清单条目 36 小时老化被裁后行号前移。缓解：回复回显队名 + `/bet 我的` 只显队名。
**不做**「编号钉死」方案（给每个 round 发永久编号）—— 那要持久化序号分配，
复杂度与收益不成比例。

### 🟡 坑 6 · `absorb_result` 改写 `teams`（§5.3 已展开）

pick 必须存队名快照。只存 A/B 会在顺序被翻时系统性判反且无报错。

### 🟡 坑 7 · 消息量与节奏

一天的消息增量 = 每场 1 条开奖（仅当有人押）。最坏情况（全员连点）被
per-user 5 秒冷却压住。**封盘不主动推消息**（v1）—— 那是消息量最大头的来源。

### 🟡 坑 8 · `bet_dry_run` 的语义

灰度开关让回复走 `console` 通道（落日志）但**状态照常变更** —— 也就是说
dry-run 期间群里真人下的注是**真计入**的，只是他们看不到回复。上线灰度时
只在「自己人演双簧」的阶段用，正式放量前必须关掉。文档写清楚，避免以后自己忘。

### 🔴 坑 9 · `/bet 我的` 在「round 配不上清单条目」时会崩（2026-10-14 自查发现）

`_bet_mine_body` 要给每一笔未结算的注标注状态，先按 `_bet_key(r)` 回清单里找
对应条目。两种常见情况会找不到：① 条目掉出了 36h 结算窗口被裁；② 队名被
`absorb_result` 用结果页的写法改写，键配不上（§5.3 的同一根源）。

**原来的写法**把三个状态分支写成一个 dict 字面量再 `.get()`，而
`bet_close_ts(it, es)` 在**构建 dict 时**就被求值 → `None.get("ts")` 直接抛
`AttributeError`。后果不是「这一行显示不对」，而是：`cmd_handle_bet` 抛异常 →
`handle_cmd_message` 记 warn 返回 `fail` → 水位线不推进 → **同一条 `/bet 我的`
每轮重试、永远回不了消息**，且只有日志里一行 warn（群里毫无迹象）。

对策（两处，都要留着）：① `_bet_mine_rows` 里 `it is None` 时老实答「待开奖」，
不猜状态；② `bet_close_ts` / `bet_round_state` 本身容忍 `item=None`
（返回一条过去的封盘线）—— 常驻命令进程不该被任何偶发配不上打炸。
自检：断言 15 钉住（seed round 的 ts 与清单任何一条都配不上，正是这个场景）。

      ⑪ **坑 9**：round 配不上清单条目 → 「待开奖」不崩，`bet_close_ts(None)` 不炸。

## 12. 上线顺序与回滚

> 前提（§1.3）：`douyu-cmd` 当前 **disabled / 未启动**。`/bet` 的全部上线动作都发生在它起来之后。

```
 0. douyu-cmd 先按 CMD_INTERACT.md §9.4 上线：
    前台 python3 esports.py --listen 手跑 → 群里 @机器人 /赛事 确认收到大图 →
    确认历史不重放 / 冷却 / 隔离 → systemctl enable --now douyu-cmd → 观察
 1. 实现 + 三自检（esports --selftest / selftest.py / watchdog --selftest）+ check-secrets 全绿
 2. commit + push（origin 走 SSH）→ python pack_deploy.py
    （BET_PLAY.md 进 REQUIRED 清单，包从 52 个文件变 53 个；2026-10-14 起
    bet_template.html 也进 REQUIRED，包为 54 个文件）→ workbench 部署
 3. 服务器 config.json 的 esports 段：bet_enabled = true，bet_dry_run = true
    （功能开着但只落日志不进群；状态照常变更，下注/积分都真实生效）
 4. 灰度：重启 douyu-cmd，群里敲 /bet —— 回复只落 `/var/log/douyu-watch/cmd.log`
    （`StandardOutput=append:`，**不是 journalctl**），逐条核对文案与判定
 5. 真人实测（dry-run 仍开着也无妨，看日志）：/bet、/bet 1 A、改单、未开放、已封盘。
    封盘边界的秒级竞态与结算幂等**用单测覆盖**，不靠群里卡点演
 6. bet_dry_run = false → 正式上线（bet_enabled = true 在步骤 3 就已为 true 的话，此刻即放量）
 7. 观察 24h：对账日志（开奖/作废/undecidable）、消息量、有无异常重试
 8. 回滚（一行）：config.json 里 bet_enabled = false → 重启 douyu-cmd。
    不停服务、不动 6 个 timer、不动 NapCat、不删状态文件（积分留着，下次开启接着来）
```

⚠️ 步骤 8 之后 `state_bets.json` 继续存在但不再变化 —— 这是刻意的：
再开启时积分和历史都还在。真想清零才手工删文件（无命令入口，防误触）。

## 14. 查询类卡片大图（2026-10-14 用户确认接入；同日第二次改版为单栏）

查询类回复（`/bet` 列表、`/bet 我的`、`/bet 排行`、`/bet 规则`）从纯文本升级为
**1920×1080 卡片大图**，视觉与 `/赛事`、开赛提醒同一套栈（`render_html_png` +
`bet_template.html` + `__BET__` 占位符 + Chromium 无头截图）。

> **2026-10-14 第二次改版（用户看过首版预览后提的要求）**：首版右侧有一栏
> 「四阶段时间线」示例，用户判定**占用近一半版面而信息量接近于零**，要求删掉、
> 单栏铺满，并且列表要画**队标**。改动落在两处：
> ① 模板整栏重写（`.tl` 区、`#stages`、`#nofocus`、`#example`、`.win` 全部删除）；
> ② 数据层删 `focus` / `win` 两个键与 `_bet_focus()` / `BET_CARD_WIN_W2`，
> 改为 `layout`（两模式）+ `empty`（空态大字）+ 行内富字段。
> 断言 15③⑦⑧⑨ 与契约断言（模板不得残留 `stages`）就是钉这次改版的。

### 14.1 四条设计纪律

1. **只升查询，不升动作**。下注/改单回执与开奖消息**永远纯文本**：动作要快
   （下注是封盘前几秒的连续操作，不值得等一次截图），且回执里没有值得画成图的
   信息。自检断言 15⑤ 用 AST 钉住这条边界（`_bet_place_body` 一个卡片符号都不碰）。
2. **卡片是文本的图形化，不是另一套口径**。头行与每一行的文案与纯文本回复
   **逐字同源**——列表行共用 `_bet_row_text`（状态栏共用 `_bet_row_status`），
   「我的」/排行共用 `_bet_mine_rows` / `_bet_rank_rows`。断言 15① 把两边摆到一起比。
   「图里说还能押、文本说已封盘」比没有图更糟。
3. **出不了图就降级，绝不外抛**。`render_bet_card` 学 `render_preview_card_html`：
   缺模板 / 没 Chromium / 截图失败 → 记日志 → 返回 None → 上层发原纯文本。
   与开赛提醒「HTML → 纯文本」两级降级同哲学（这里连 Pillow 中间档都没有：
   880px 那套画的是赛程，画不了竞猜状态）。
4. **队标只看缓存、不联网**（这是改版时新增的纪律）。`/bet` 是群里**随时**的问答，
   有人问一句不能就去抓十几张图 —— `_html_logo_cached` 只读 `logo_cache/`，
   命中返回 `file://` URI，没命中返回空串让模板画占位块。缓存通常已被当天
   09:30 的总预告预热（同一批比赛、同一批 URL），所以实际几乎总能画出来。
   `/赛事` 那条线用的是会下载的 `_html_logo`（有 `logo_max_new_per_run` 预算兜着），
   两者**刻意分开**，断言 15④ 用 AST 钉住。

### 14.2 版面（单栏铺满，两模式）

| 区域 | 内容 |
|---|---|
| 头部 | `CS2 /BET 竞猜` + 日期 + `V2 时间规则` 签 |
| 横幅 | v2 规则一句话（按 `bet_close_before_start_minutes` 现算，与 §2.5 文案同源） |
| 面板头 | 回复头行（大字号）+ 右上角命令气泡（`@机器人 /bet` 等，按 kind 参数化） |
| 面板体 | **`layout="rows"`**（列表/我的）：一场一行，列 = 序号 · 开赛时间 · **队标+队名** · `VS` · **队名+队标** · 状态栏（封盘时间 / 结果 + `Bo3`）· 状态胶囊。行高由 `flex:1` **均分**，把整张图填满；字号/队标按行数分三档（≤3 / ≤6 / ≤9 / 更多） |
| 面板体 | **`layout="fill"`**（规则/排行）：大字号行，左标记（规则=绿点、排行=名次）+ 主文案 + 右侧分值。**字号自适应**：`min(byRow, byWidth)` 再夹到 30~96px —— `byRow` 保证 n 行塞得下，`byWidth` 保证最长那行**单行放下**（折行会让规则读起来断断续续），字宽按「全角 1 / 半角 0.62」+ 6% 余量估算 |
| 空态 | 一行都没有时居中大字（`empty`），**不再重复底部说明** |
| 面板底 | note（「后附 N 场…仅供对照」等）+ 命令提示（仅在有行时显示） |
| 页脚 | 数据来源（服务器赛程状态，零网络查询）+ 生成时刻 |

⚠️ **去掉了右栏时间线**：首版那栏每张图都画同一套「总预告发布 → 封盘 → 开赛 →
起抓结果」，四种 kind 只有焦点场次不同 —— 信息密度极低而占掉近一半宽度。
改版后四种 kind 共用同一套单栏版面，差异只在 `layout` 与行内容。

### 14.3 接入点与开关

- `cmd_handle_bet` 的四个查询分支统一走 `_bet_query_reply`：先算纯文本 body
  （与升级前完全相同的函数），再 `bet_query_card()` 构图渲染，最后
  `_bet_reply(cfg, es, msg, body, png)` —— 图通过 `with_card_image` 挂在
  **onebot 通道**（base64 内联，NapCat 在 Docker 里看不见宿主路径），
  与文本同一条消息（`[CQ:reply]` 前缀 + 文本 + 图）。
- 开关 `bet_card_enabled`（默认 `true`）：关掉后查询回到纯文本，一行不少。
  dry-run 时日志会多打一行 `（+ 卡片图 N KB）`，灰度期能确认图真的渲染出来了。
- 模板 `deploy/bet_template.html` 进 `pack_deploy.py` 的 REQUIRED + FINGERPRINT
  与 `install-watch.sh` 的拷贝清单（部署包 53 → 54 个文件）；`_TPL_SPECS`
  自检认 `__BET__` 占位符（与四张大图各认自己的那个同一套路）。
- **零网络不受影响**：截图是本机 Chromium，不是网络请求；断言 7 的
  `_bet_fns` 元组已把卡片/富行/队标那六个函数加进去，照样一个抓取符号都不许出现。

### 14.4 已知局限

- 卡片行数跟随 `bet_max_list_rows`（默认 12）：列表文本列几行，卡片就列几行，
  「另有 N 场不逐条列出」的说明同步搬过去。行多时字号/队标自动收一档（≥10 行
  收到最小档），不会再撑破。
- 队名沿用 `_clip`（16 字）截断，与纯文本一致 —— 卡片上长队名会显示成
  `Team Falcons vs Ninjas in Pyjam…`，这是**刻意的**（同源优先于好看）。
- `/bet 排行` 卡片的高亮是前三名，纯文本没有这个视觉 —— 属于**纯装饰差异**，
  文案仍逐字同源。
- 队标只在**当天总预告预热过**的情况下出现；冷缓存（比如刚重启后立刻有人问）
  会画成带短名的占位方块，不影响其余信息。
- 截图耗时约 1~3 秒（本机 Chromium），串在命令处理里。`douyu-cmd` 单轮
  串行处理，最坏情况是这一轮多花几秒 —— 与 `/赛事` 大图同一量级，可接受。
